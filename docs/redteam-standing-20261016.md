# 红队常驻化提案（2026-10-16，卡 t_26622aac 交付件；**提案不执行，待用户裁决**）

> 背景：#278 首轮红队（纯本地数据）与 #292 红队正式版（补上 LLM 出题环节，76 条 kill condition）均为**一次性**动作——红队的价值在「重复」，一次性扫描的结论会随时间和新线注册迅速过期。本文设计三种常驻形态并给出推荐。
> 纪律：本提案不改生产规则/参数/权重，不建 cron；形态选型与触发条件待用户裁决后写入 `docs/plan/DECISIONS.md`（O-09）。

---

## 0. 先定「红队常驻要解决什么」

一次性红队的产出有两类，常驻形态要对准其中**会过期的那一类**：

| 产出类型 | 会过期吗 | 常驻是否值得 |
|---|---|---|
| **A. 口径/实现层缺陷**（如 #292 证实① 三档净值漏计最低佣金 drag、⑤ 摇篮线日集中） | 修掉即消失，但**新写的代码会引入新缺陷** | 值得——针对**新增/改动**代码的差分审 |
| **B. 样本量/独立性证据**（如 #292 证实② 单票归因被打死、③ n=48 无统计证据） | **必然过期**（n 随影子累积增长，判词会翻转） | **最值得**——这是随数据自然推进的检查 |
| **C. 结构性威胁**（如 ⑥ 深档单窗口驱动、⑦ 转债 CC 级） | 状态型，变化缓慢 | 中等——融入 #283 监控机即可 |
| **D. 信号本体 edge 存亡** | 由 #283 生命周期监控机负责 | **不重复**——红队不抢监控机的活 |

结论：**红队常驻的不可替代价值 = B（样本量证据的到期重算） + A（新增代码的差分审）**。C 交给 #283，D 已有 #283。

## 1. 三种形态

### 形态 A：每周定时全身扫描
**做法**：每周一 21:40 BJT 自动重跑 #292 的 39 条实跑项 + 逐条重判 37 条待跑项（待跑项需先补齐数据源）。

**成本**：
- 39 条实跑项：纯读已有产物，实测 `adjudicate.py` + `adjudicate_supp.py` 两脚本 **<20s** 跑完；
- 37 条待跑项**当前不可跑**（缺逐笔账本/原始产物）——即 A 形态首年会**长期只有 39 条在跑**，另 37 条是死重；
- 真正的大头是「补齐数据源」的工程成本（PORT-01 逐笔账本当属其中，~1 人日）。

**问题**：与 #283 日频监控机在「读产物文件」上重叠；而 39 条里的多数（口径类）本来就不会周级变化。**周频颗粒度过细、覆盖面过窄。**

### 形态 B：每注册新线自动触发审该线
**做法**：在 `law_pipeline.py` 的 REGISTRY 新增线时（submit 四件套通过后），自动跑该线的**三条标配 kill condition**：

1. **样本量充分性**：独立出票日 ≥ 20？（#292 kc35 教训——55 单只有 8 个独立日）
2. **单票集中度**：剔除最大贡献单票后 edge 是否存活？（#292 kc23 教训——剔 000338 后几乎无变化，说明「别修单票冷却」）
3. **日历去重后显著性**：日等权口径下 edge 方向是否不变？（#292 kc52/53 教训——LD 影子扎堆 17 日，去重后仍负）

**成本**：~150 行（挂在 submit 后，只读 REGISTRY 已有的回测产物 + claims_shadow 同口径），复用现有 `claims_audit.marginals` 与 law_pipeline 的事件结构；零新依赖。

**价值**：把 #292 的三条最硬的教训**前置到注册流程**——「画像≠edge」的纪律从口头变成自动门。

### 形态 C：挂进信号生命周期监控机（#283，兄弟卡 t_6f42f1a1）当威胁探测器
**做法**：把 #292 的 76 条 kill condition 中**可自动重算的子集**注册进 `engine/line_health.py` 的监控项，与现有 T1-T7 并列：

- #283 已有 T1-T7 = #278 的七条证实威胁（读既有产物文件、文件缺失优雅降级）；
- #292 新增的威胁（①三档 drag 缺口、⑤摇篮线日集中、⑥深档窗口集中、⑦转债 CC 级）**同样是「读一个产物文件比一个阈值」**的形态，与 #283 的架构完全同构；
- 阈值机纪律一致（连续 N 次触发才产提案，不自动执行）。

**成本**：~80 行（reuse line_health 阈值机框架）+ 1 个待跑清单文件（把 37 条结构化，标 `no_data` 优雅降级）；**零新架构**。

## 2. 推荐：C 为主 + B 为辅（不推荐 A）

| 维度 | A 周扫描 | B 新线触发 | C 挂 #283 |
|---|---|---|---|
| 覆盖的过期风险 | 口径类（变化慢） | **样本量类（必过期）** | 结构性（变化慢） |
| 实现成本 | 高（需先补 37 条数据源） | 低（~150 行） | 低（~80 行，复用） |
| 与 #283 重叠 | 高 | 无 | 本就是一体的 |
| 触发时机 | 固定周频（可能空转） | 事件驱动（精准） | 日频（与监控机同步） |
| **建议** | **否** | **是（辅）** | **是（主）** |

**推荐方案**：
1. **主形态 = C**：把 #292 的 76 条 kill condition 结构化落成 `data/redteam_watchlist.json`，每条带 `kind`（`readable` / `needs_ledger` / `needs_raw` / `heavy_compute`）与 `recheck_cmd`；`line_health.py` 消费其中 `readable` 子集（#292 的 20 条实跑可重算项），其余标 `no_data` 等待数据源补齐。触发时机与 #283 同步：**每月首个交易日 21:40 BJT**（排在 line_health 之后），或 REGISTRY 变更时立即。
2. **辅形态 = B**：新线注册时自动跑三条标配 kill condition，任一不过 → 注册流程要求显式记「已知弱证据」并写入 `line_health` 的初始 grade。
3. **不建 A**：周频全身扫描与 #283 重叠且 37 条待跑项补齐前无效。

**为何不用「每周」**：本仓 34 条存活线的 edge 是月级更新量（影子结算周期 T+5/T+20），周频重算的方差大于信号变化本身——#292 自己就证明过「n=11 的单年数字全靠右尾」。**降频到月**反而更少误报。

## 3. 需用户裁决的点（写入 DECISIONS.md O-09）

1. **形态选型**：是否采用「C 主 + B 辅」（推荐）？或坚持 A？
2. **是否先补 PORT-01 逐笔账本**：#292 有 8 条 kill condition 卡在逐笔账本上（A1/A5/A6/D4），补了才能把 `needs_ledger` 类转为可自动重算——**这是常驻化覆盖率的分水岭**（20 → 28 条）。
3. **QQ 告警口径**：#283 现有设计是「新增触发才说话」（看门狗模式）。红队威胁探测器是否沿用（推荐沿用以守 D-11 注意力预算），还是红队类单独日报？
4. **红队 LLM 环节是否每月跑一次**：本卡用 wb2api（DS-v4.1-pro）出题成本 = 4 组并发、约 70s/组。每月一次全量出题的边际价值 vs 常驻成本——建议**每季度一次**（红队出题的质量取决于题面新鲜度，同一批结论月月出题会退化成复读）。
5. **wb2api 凌晨 1-6 点禁用窗口**与「每月首个交易日 21:40 BJT」不冲突；但若改到凌晨跑（低负载）需避开该窗口。
