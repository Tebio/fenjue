# 施工方守则（CONSTRUCTOR BRIEF）— 开工前必读

> 这份文件是给**施工方**（外部 AI / 子代理 / 任何执行者）的。
> 主 agent 的验收清单比这严得多，本文件只写「怎样让你的交付一次通过」。
> **读完这一段才能动手。违反其中任一条，交付会被整包打回。**

---

## 一、开工前：先对齐，再动手

1. **读完任务书指定的每一份文件**（spec、对标基线、注册表、现有实现）。跳过不读是返工的第一原因。
2. **有异议先按任务书做**，然后在报告里写明理由和你的替代方案。**不许自作主张改设计**——你觉得更好的方案，主 agent 可能已经权衡过。
3. **发现硬约束互相矛盾**（比如「禁联网」又要求「跑带行情请求的生产脚本」），**立刻在报告里提出，不要二选一硬扛**。

## 二、施工中：四条铁律

4. **改任何既有文件前，先留 `.bak`**。任务是「改 A 改 B」就逐个文件留，不是只给第一个留。
5. **禁止 `python -c` / `-e` 内联**，一律写成 `.py` 文件再执行（内联脚本无法审计、无法复用、无法 diff）。
6. **不许为了让检查变绿而削弱断言**。禁止把 `assert==200` 改成只打印、把严格比较改成 `>=`、把异常分支吞掉。改了测试必须逐行在报告里说明改了什么、为什么。
7. **不许碰任务书「不许碰」清单里的任何东西**，包括只读的数据目录（`data/big_kcache/` 这类）。

## 三、交付前：自己先对账（最容易被抓的一条）

8. **交付物清单必须完整、逐文件**，四类都要列：
   - 新增了哪些文件
   - 修改了哪些文件（**逐个列，不许合并成「若干」**）
   - 删除了哪些
   - 留了哪些 `.bak`
   然后**自己跑一遍 `git status --short`**，把输出里的每一条回到你的清单里找出处。
   > 实测教训：改了 5 个文件、清单只列 4 个，漏的恰好是一个既有测试文件。主 agent 是靠 `git status` 发现的——**漏报比做错更伤，因为验收方会按你的清单放行**。

9. **每条结论后面必须跟命令或文件证据**。不许写「应该」「大概」「已确保」「理论上」。
   - ✗ 「已确认注册表未被修改」
   - ✓ 「`md5sum data/datasets_registry.yaml` → `e698cc6d...`，与施工前一致」

10. **接口写好 ≠ 已验证**。这两句必须分开报：
    - 「函数签名已实现、单测通过」
    - 「用真实生产入口跑了一次，输出是 XXX」
    只做第一件就说「完成」= 打回。

11. **覆盖度如实报告**：几个成功、几个失败、哪几个没做完。**不许把 3/4 写成「基本完成」**。
    没做就说没做，卡住就说卡在哪——这比含糊交差有价值得多。

12. **遇到说不通的矛盾，如实写「这条矛盾未解」，不许编解释**。
    > 为了交差虚构机制，会变成下一轮排查的假前提，比留一个问号危险得多。

13. **你主动标注的「这条我不确定 / 需要裁决」的每一处都会被主 agent 逐条判**，写上它们（这是最有价值的部分，别藏）。

13. **最后一步改动任何文件之后，必须重跑一遍总闸才算完成**（台账、AGENTS、文档都算）。
    > 实测事故：施工方跑完 `verify.sh` 得全绿，随后往 `AGENTS.md` 追加台账（引用了新建的任务号），
    > **没重跑**，于是报告写「全绿」而实际是红的（任务号在 backlog 里没有条目 → 悬空引用检查报红）。
    > 这类失败的形状是「每个动作都做对了，只是顺序把它变成谎言」——**改完最后一笔，从头跑一遍**。

## 四、报告固定结构

```
## 一、交付物清单
新增:   <文件> — <一句话作用>
修改:   <文件> — <改了什么>（.bak: <路径>）
删除:   <文件>
未申报检查: git status --short 输出已逐条对账，无遗漏 / 有漏项已补

## 二、实跑证据（每条：命令 → 真实输出）
（贴原始输出，不要转述）

## 三、覆盖度
成功 N 项 / 失败 M 项 / 未做 K 项
失败与未做的原因：

## 四、我不确定 / 需要裁决的地方
1. ...

## 五、踩的坑（供下一个人参考）
1. ...
```

---

## 五、为什么这么严（看一下，别当形式）

上一轮施工方发生过的真实事故，全部写在这几条守则里：

| 事故 | 后果 | 对应条款 |
|---|---|---|
| 改了测试文件但没写进交付清单 | 验收方差点放过一处未审的断言改动 | 8 |
| 改既有文件没留 `.bak` | 出问题只能靠 git 回滚，丢失工作区状态 | 4 |
| 报告写「已验证全绿」实为接口级验证 | 上线后才发现真实入口跑不通 | 10 |
| 把「4 个里 3 个通过」写成「基本完成」 | 缺口被带进下一轮，越滚越大 | 11 |
| 「昨天绿今天红」时给出想当然的解释 | 真正的根因被掩盖，下一轮照着假前提排查 | 12 |

**结论**：技术能力不是主要风险，**申报纪律**才是。清单完整 + 证据可查 + 覆盖度诚实，三者齐全的交付，即使有 bug 也能快速定位；缺其中任何一个，验收方只能全量重查。
