## P0：三源生产者决策与落地

每个源独立决策，**二选一或混合**：

**路线 A：自动化**——建 cron 生产班。判断依据：消费者是不是生产链路的、数据时效需求多强、抓取成本多大。
**路线 B：改声明**——把 cadence/max_lag 改成与手动现实相符的节奏（如 weekly），并在 owner 注释里写明「手动抓，抓完更新末端日期」。

我给的倾向性判断（你可以反驳，给出理由）：
- **fund_cache → 路线 A**。law_pipeline 是生产信号管线，基本面缓存停一个月意味着信号在用过期的 PE/PB。但注意：手动分片抓 3377 只**可能有反爬/限流**，先小批量试抓（50 只）确认源还活着、评估全量耗时，再决定班次频率（daily 全量可能不现实，weekly 全量或 daily 分片轮转都行）
- **cap_hist → 路线 B 或低频 A**。流通股本历史变化很慢（只有送转/增发才变），weekly 足够
- **kcache → 路线 B**。owner 写明「随取随更」，那就把 cadence/max_lag 改成与之一致，别让它每天报 0%

**硬性要求**：
- 新建的抓取班必须实测跑通（exit 0 + 数据末端日期推进 + 不触发目标站反爬）
- 抓取脚本如果本来就不工作了（接口变了/源没了），**如实报告**，不许假装能抓
- 改声明的，golden 如有冻结需要重录，留证据链（沿用 #352 的做法）
