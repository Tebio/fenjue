# 派单与审计协议（2026-10-20 立，依据两次实战翻车）

> 立的理由：2026-10-20 一天内出现两类可避免的返工——
> ① 我写的 spec 自相矛盾（回测族同时被列入"拒写"和"豁免"），K3 施工时才发现；
> ② 我的审计脚本没有复现被测对象的真实前提（没刷新体检），三场景全假 FAIL。
> 两条都不是能力问题，是流程缺环节。本协议把缺的环节补上。

## 一、派单前：spec 自检（5 项，缺一不许派）

派单前**必须自己先当一次审稿人**，逐项过：

1. **矛盾 lint**：同一对象是否在不同段落得到相反处置？
   （实例：`回测族` 在 R1-① 被列拒写、在 R1-③ 被列 EXEMPT。）
   做法：把 spec 里所有"某对象 → 某行为"的映射抽成表，看同一 key 是否出现两个 value。
2. **契约自洽**：接口表（附表）与正文叙述是否一致？**附表通常后写，以附表为准**，
   但要回头把正文改掉，不能留两套。
3. **可验证性**：每条验收标准是否能用一条命令证明？写不出命令的标准等于没标准。
4. **前提完整性**：验收步骤是否依赖未写明的状态？（实例：熔断验收依赖"体检已刷新"，
   而 spec 没写这一步 → 审计方自己踩坑。）
5. **硬约束是否会被自身任务违反**：约束之间冲突吗？
   （实例："严禁联网" vs "dashboard_build 必须端到端"——面板构建固有只读行情 GET。）
   冲突时**在派单前裁决**，不要留给施工方临场判断。

## 二、任务书必含七段

1. **读什么**（按顺序，含"唯一真源"标注）—— 不读完不许动手
2. **已知勘察结论** —— 主 agent 已经查明的，省重复劳动；但要标明"可质疑"
3. **施工内容** —— 分优先级，"必须端到端" vs "接上线即可"写清楚
4. **硬约束** —— 每条都能被机械检查
5. **必须实跑并贴输出** —— 逐条列出场景，禁止"应该""大概"
6. **交接要求** —— backlog / AGENTS / 覆盖度如实报告（接口写好了 ≠ 已验证）
7. **异议机制** —— 明文写："认为 spec 有错先按 spec 做，然后在报告里说明并给理由，不许自作主张改设计"

## 三、交付后：主 agent 审计三件套（不许用施工方的验证代码）

| 审计 | 做什么 | 为什么不能省 |
|---|---|---|
| **静态** | AST 读实现：关键常量是否**字面量**写死、是否 import 唯一口径、异常分支是否真 raise、下游是否真接线 | 施工方可以在测试里造一个合规的世界，代码本体却走了另一条路 |
| **端到端** | 自己构造场景（改坏数据/伪造缺失）跑真实入口，用 **md5/mtime 前后对比**判断"真没写"还是"写了又删" | 报告里的"已验证"是自己说的，不是事实 |
| **还原校验** | 所有被审计改动必须能还原，注册表/数据 md5 与基线逐项比对 | 审计本身会污染生产；没还原的审计等于事故 |

**审计铁律（今天用真金白银换的）**：
> **审计脚本必须复现被测对象的真实前提条件，否则测的是自己搭的假场景。**
> 实例：熔断读的是缓存的体检结论，我改坏注册表却没重跑体检 → 读到旧 ok → 三项全 FAIL，
> 全是假阴性。加上"刷新体检"后立刻全 PASS。**FAIL 先怀疑自己的场景，再怀疑对方。**

## 四、常见失败模式（本仓库实证，遇到先查这几条)

| 症状 | 病根 | 对策 |
|---|---|---|
| 报告全绿但生产没效果 | 检查器在空输入上返回通过（`all([])==True`） | 空集合必须显式判"未审计"，不许判通过 |
| 状态/结论长期不变 | 检查器根本没被执行（wrapper 改完没验证） | 检查器要有"我跑过"的落盘痕迹 |
| 改配置后行为不变 | 依赖**手写**的版本号/标志位当一致性凭证 | 用内容哈希（`registry_fingerprint`） |
| 审计账本越用越乱 | 同日重跑无条件 append | 幂等：同日覆盖（`append_history`） |
| 判死代码判错 | 只按 cron 引用判，忽略 import/动态引用/手动工具 | 四分类：生产/库/有近期产物/疑似死，**判死只登记不删** |

## 五、纠错授权（用户 2026-10-20）

允许在项目中纠错，不必事事请示。**可直接改**：文档/注释/测试/死代码登记/版本控制纳入/契约矛盾处。
**需要先说**：删数据、改生产脚本行为、改 cron 调度、重写既有实现。
**永不擅自**：删 `big_kcache`/`k4_panel`/`big_kcache_unadj`、改 docker-compose、动用户持仓数据。

## 六、并行与后端选择

- 难题派 K3（额度大、能自己跑命令验证），执行/红队用 V4.1，复杂结论可开 MOA 对审。
- K3 跑长任务用 `background=True` + 完成后审计；**不要边跑边改同一批文件**。
- 子 agent 默认不派（用户规定）；派了必须独立文件 + 自定义事件契约，避免冲突。
