## 1. P0 三源决策与实测

### fund_cache → 路线 A（自动化日更），与派单倾向一致

**理由**：消费者 law_pipeline 是生产信号管线（`_fund_healthy` 用信号日或之前最近的 peTTM/isST 剔亏损/ST），
缓存停一个月 = 10 月信号全用 9 月估值。baostock 源实测活着（600000 试查返回 10-20 行）。

**落地**：
- `engine/fetch_fundamentals.py` 新增 `--update [limit] [k/N]` 增量模式：尾读 300B 取末 bar 日期
  （freshness_core._tail_last_date 同款，避免每晚全量 json.loads 580MB）→ 从末 bar 当天重抓、
  按日期去重合并（愈合半截末日）→ tmp+os.replace 原子写；末端已是最新交易日的票跳过（幂等重跑零请求）；
  71 个空占位文件跳过；big_kcache 新票全量补抓（保留 <60% 对账告警）。
- 分两片对齐 cron 3600s 墙钟（试抓实测 ~1.15s/只，单片 ~1680 只 ≈ 32min）：
  - 片0 cron `39217e893ed1`（00:45 BJT = 16:45 UTC，wrapper `stock_fund_update0.sh`）
  - 片1 cron `730473253554`（01:50 BJT = 17:50 UTC，wrapper `stock_fund_update1.sh`）
  - wrapper 纪律照 stock_unadj_fetch.sh：venv exec + baostock 独占守卫（等 15 分钟还占着就 exit 1 报红，不双进程）
- 班次卡位：00:45/01:50 BJT 落在不复权断言班（00:20 BJT）之后、全天无其他 baostock 班的空窗。

**实测证据**：
- 50 只试抓：57s、ok=50 fail=0；落盘校验 000001/000002 末 bar 2026-10-20（peTTM 5.108/-0.449 等实值），
  日期无重复且有序；停牌股 000004 末 bar 停 07-13（重叠重抓返回既有行，合并无变化，不死循环）。
- 首晚全量真实调度回填：`hermes cron run 39217e893ed1` → completed（execution 9df4b994，
  18m47s，stdout `done ok=1625 fail=0`，证据 /opt/data/cron/output/39217e893ed1/2026-10-21_00-49-14.md）；
  片1 `hermes cron run 730473253554` → 见 §5 验收汇总。
- 无反爬触发：全程 fail=0，无 error_code 非零重试风暴。

### cap_hist → 低频路线 A（增量周更），与派单「B 或低频 A」一致

**理由**：消费者是 factor_research/seat_gene 等研究线，非日频生产；流通股本只在送转/增发时变，
weekly 足够。但既然增量机制已为 fund_cache 建好，同构复用成本极低，自动化比「手动+改声明」更不易再腐。

**落地**：
- `engine/fetch_cap_history.py` 新增同款 `--update [limit] [k/N]`（行格式 [date, close, 流通市值亿]；
  全量补抓保留原 <60% 截断不落盘校验）。
- 周六两班：片0 cron `525e9eb40955`（09:30 BJT）、片1 `35fbb0e3cca2`（10:40 BJT）。
- 注册表声明对齐：cadence daily→weekly，max_lag 5 不变（周六班后滞后≤5 交易日；漏跑一周次周一起 stale，
  预警语义正确）。

**实测证据**：50 只试抓 47s、ok=50 fail=0；000001/000002 合并到 10-20（流通市值 2220.1/335.2 亿），
日期去重有序。首轮回填 cron run 证据见 §5。

## 3. P2 xrules OOM 缓解

**方案选择：错开班次**（xrules 20:15→**20:22 BJT**，job 036130e2e17b 已 edit，名同步改注）。
理由：①实测 regime 班 118s、xrules 单跑 94s（executions.db），12 分钟间隔 = 6× 余量，连 20:35 体检班也不挤；
②ulimit -v 被拒——numpy/pandas 大量 mmap 虚存，-v 限制会误杀正常进程，且内存耗尽被杀中途可能写坏 state 文件；
③拆片改动大收益小，xrules 单跑 94s 根本不慢，病在「同驻」不在「本身重」。
**教训入账**：本单施工期间两次手动 `cron run` xrules 与抓取班并发，各吃一次 SIGKILL(-9)——
实证了「重班同驻即 OOM」的触发面不止 regime×xrules 一对，手动触发重班也要避讓。
